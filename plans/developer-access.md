# Developer access

Updated: 2026-10-15.

Status: local implementation only. The user requested Developer access equal to Administrator, with a password required at every sign-in. Deployment remains on hold until the user explicitly says **deploy**. Runtime `pcn-test-17-1` and its host configuration are unchanged. The Records dashboard checkpoint is also local; neither feature has been released by this work.

## Role and assignment

Developer is stored as the exclusive role `developer`, department `developer`, and no signing-step assignment. It is not stored as `admin` and cannot be combined with another role, department or signing step. Existing employee-backed, PCN-local and eligible password-maintenance accounts can receive this explicit assignment through the normal account-management APIs.

Developer has the same application permission checks as Administrator: Portal, Users, Mail Routing, record management and authorized administrative workflow/signing actions. Existing record versions, terminal locks, signing order, document-control, current-account and session checks still apply. Administrator-equivalent access does not invent completed signatures or bypass validation.

Users supports Developer in Add role, Create user, Edit access and role/department filters. Selecting Developer sets the Developer department and removes the signing-step assignment. Profile and access labels display Developer. Existing verified-email and account-creation requirements continue to apply.

Developer is excluded from automatic signing-mail routing because it has no department signing assignment. Existing manually managed Mail Routing remains an administrative capability. Assigning Developer does not automatically make that account an automatic workflow recipient.

The last-active-employee-Administrator guard still counts actual Administrator grants. Developer cannot substitute for the final Administrator; converting or removing that final grant remains blocked. Assignment changes retain the existing session-revocation behaviour.

## Sign-in and session lifecycle

Normal identity verification runs first. Source-backed employee accounts still require current employee-source verification, PCN-local accounts use their established local-account checks, and password-maintenance accounts still require their normal account password. Developer then requires the additional configured Developer password before a session can be issued.

The password is a shared private Developer credential configured for this installation, not an account password saved on each PCN user. The browser reveals a password challenge when the authenticated identity needs Developer verification. It clears the challenge on identity changes, cancellation and page exit, and does not store the password in preferences or browser storage. Non-Developer accounts keep their existing sign-in behaviour.

The server never accepts a client flag as proof of Developer verification. Successful verification produces private server-side proof bound to the current account/security stamp, credential version and resulting session. Protected requests still validate the account and session and require matching proof. Incorrect passwords use the existing failed-sign-in/lockout handling.

Developer proof is held in a bounded private in-memory session cache. A server restart clears proof even if a database session or browser cookie remains. Rotating the configured hash invalidates proof for the previous credential. In both cases, Developer must sign in again; a surviving cookie cannot bypass the password gate. This cache design is for the current single-process installation: multiple independently running workers would require a deliberate shared proof/session design.

## Private configuration

`PCN_DEVELOPER_PASSWORD_HASH` contains only the encoded Argon2id hash of the selected Developer password. Set it through protected process configuration or the installation's private environment file, never through browser responses, source, release archives or committed examples. [.env.example](../.env.example) intentionally leaves the value blank. No password or real credential hash is included in this document.

The current configuration validator accepts Argon2id version 19 with memory cost 65536 KiB, three iterations, parallelism one, a 16-byte random salt and a 32-byte digest. The encoded iteration and parallelism fields may appear in either order after the memory field, including the order generated by the production password hasher; costs and lengths must still match exactly. Generate a fresh hash with the project's Argon2 library using those parameters, then store it directly in private configuration. Do not print or save the plaintext password in commands, logs or documentation. An arbitrary encoded hash with different parameters is not accepted by this validator.

Missing, blank or malformed hash configuration disables Developer sign-in only. Existing employee/password authentication for other roles continues. The public authentication configuration exposes the sign-in mode, not the hash or Developer credential. Apply a reviewed private configuration change and restart the local process when changing its environment; previously verified Developer sessions must then sign in again.

The Developer hash was configured in the ignored local environment file after masked-input password hashing, real password verification and configuration validation succeeded. A fresh child process loaded the local environment and confirmed valid Developer configuration without printing any password or hash. This local setup applies no migration and grants no account access. The committed template remains blank. No host configuration, certificate or HTTP change is part of this feature.

## Database prerequisite

[007_developer_role.sql](../sql/migrations/007_developer_role.sql) seeds `developer` in `pcn.Roles` only when absent. It grants no user access and contains no table/column change. It is appended to the migration manifest; existing migration files and checksums are unchanged.

**Migration 007 is prepared, not applied.** Current SQL-backed source expects it during schema validation. An existing database with only migrations 001–006 requires the separately authorized migration before this source can start; providing the private password hash alone does not satisfy that prerequisite. Startup and deployment do not silently run the migration. No SQL migration, account assignment or live business-data mutation was performed as part of this implementation.
